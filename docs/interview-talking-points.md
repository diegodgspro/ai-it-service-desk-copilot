# Interview talking points

**30-second introduction**
“I built this personal support lab to make incident triage and troubleshooting recommendations visible and reviewable. It covers common endpoint, identity, network and application incidents. A lightweight local classifier and versioned knowledge articles support the technician; business-impact rules and human approval control the workflow.”

**What is actually AI?**
TF-IDF features plus a trained logistic-regression classifier predict the support domain. Retrieval uses document similarity. The default troubleshooting and user response are curated/template-based, not generated by a large language model. Optional Ollama enriches narrative fields. It does not control priority or actions.

**Why not a vector database?**
Nine articles do not justify another service. Local TF-IDF retrieval is inspectable and sufficient for a focused demo. I would evaluate retrieval failures and scale before introducing embeddings.

**Why is the VPN incident P3?**
One user is affected with high urgency. The documented matrix maps Low impact × High urgency to P3. Priority reflects business impact and urgency, not the support category alone.

**How do you prevent unsafe automation?**
There is no execution bridge in the dashboard. Actions are allowlisted simulations. Approval is tied to the current analysis and invalidated when inputs change. Standalone remediation scripts default to dry run and require an explicit execution switch and confirmation in a separately authorized Windows lab.

**How would you integrate ServiceNow or Jira?**
Implement the normalized connector contract, translate impact/urgency and workflow statuses, use least-privilege authentication, distinguish internal notes from user-visible messages, and test retries and writes in a sandbox. Those production adapters are not implemented here.

**How did you validate it?**
Regression tests cover all eight authored scenarios, the full priority matrix, uncertain/security routing, action decisions, resolution validation, mocked LLM failures and real Streamlit interaction state. They do not establish production accuracy. Consult `docs/validation.md` for the actual run.

**What are the main limitations?**
Small synthetic training set, incomplete out-of-domain detection, no calibrated confidence, no real remediation, no enterprise auth, session-only state, and no live LLM verification in the build environment. An LLM can still produce an incorrect draft despite valid JSON.

**What would you improve first?**
Collect consented, de-identified evaluation tickets; add independently labeled multi-issue and unfamiliar-language cases; evaluate uncertainty and retrieval quality; then build one sandbox ITSM adapter. Measure technician review time and correction rates before claiming efficiency gains.

**Experience versus project**
Describe your employment history separately. Do not say this application was used by a current or previous employer. Be ready to explain and modify the priority matrix, one runbook, the provider boundary and the mock connector yourself.
